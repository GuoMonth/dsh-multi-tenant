# v0.3 P0 底座

v0.3 要把项目从 Multi-Tenant Runtime 推进成可组合 SaaS Framework 的基础。本文件固定工程方法与长期有效的 P0 规律；具体 implementation 只要后续 vertical-slice evidence 证明有更好的全局结构，就仍然允许重构。

## P0 目标

P0 回答三个架构问题：

1. **Composition** —— SaaS capability 如何声明、校验并映射到真实 Runtime scope，同时不再造第二套 DI Container。
2. **Operation** —— 一个 canonical Principal 如何拥有一次用户可见工作，并通过 one-shot lifecycle boundary 驱动 DSH create / resume。
3. **Fail-fast validation** —— 非法 capability graph 与真实 canonical creation drift 如何在用户流量进入前失败。

Distribution、Marketplace、安装 UI、vendor-specific Auth、production provider breadth、billing、audit、usage 产品都不是 P0。

## 强制开发顺序

```text
Spec
  ↓
Assumption Ledger
  ↓
Executable external probe / contract test
  ↓
强类型 + 状态模型
  ↓
Failing behavior test
  ↓
最小实现
  ↓
Vertical-slice CI proof
```

只要 public API 依赖的 blocking external assumption 在 `v0.3-assumptions.json` 里仍是 `open`，这个 API 就不能定型。

这条链不是单向流程。后续 vertical slice 如果推翻了早期数据模型，应直接重构模型并更新 live Spec，而不是为了 prerelease compatibility 保留包袱。

## Evidence 分类

- **External probe** —— 在精确支持 baseline 上证明 DSH / Cordis 拥有的行为；
- **Contract test** —— 独立于具体 production implementation，证明仓库拥有的 replaceable seam；
- **Conformance test** —— 证明 isolation / publication / teardown / locality 等跨组件 invariant；
- **Vertical slice** —— 证明真实 Principal -> Operation -> DSH execution path；
- **Packed consumer smoke** —— 证明 npm tarball 暴露并执行与 workspace source 相同的 contract。

读 upstream source 适合发现 hypothesis，但不能代替 blocking assumption 的 executable proof。

## P0 架构边界

```text
Typed CapabilityToken<T, Scope>
      ↓
SaaSDefinition
      ↓ compile
CompositionPlan
  ├─ whole-plan fingerprint
  └─ scope-local dependency-closure fingerprints
      ↓ materialize
Tenant / Principal capability graph
      ↓
Principal-owned one-shot Operation
      ↓ typed immutable capability snapshot
DSH ownerCtx / Agent setup-publication seam
```

Composition 负责 semantic capability identity、provider selection、scope placement、dependency validation、local canonical creation identity 与 bootstrap ordering。Service resolution、Context isolation、Fiber lifetime、cleanup 继续属于 Cordis。

**禁止新增第二套 ServiceRegistry / ProviderContainer / generic DI resolver。** 如果设计开始复制 Cordis，说明抽象方向错了。

## 长期有效的 P0 决策

### Capability Identity 必须 Typed + Semantic

一个 capability 通过 `CapabilityToken<T, Scope>` 同时绑定 stable Cordis service key、TypeScript value type、lifecycle / authority scope。

这样可以删除 `require<MyType>('credentials')` 这类 caller-side type assertion，也避免 key / scope metadata 各处独立漂移。

Typed helper 只是 Cordis 薄 facade，不拥有 resolution。

### Scope 必须是真实 Ownership

`deployment | tenant | principal | operation` 是真实 lifecycle / authority level。Ambient external capability 只允许 deployment；非 deployment provider 必须真的在声明 scope 内 materialize。

### Canonical Composition Identity 必须 Local

Whole Plan fingerprint 适合 exact comparison 与 diagnostics，但用于 parent canonical identity 粒度过粗。

Canonical Tenant / Principal creation 使用 **scope-local provider dependency closure**：

```text
scope-owned providers
+ 它们真正依赖到的 selected ancestor providers
```

因此无关 Operation 演进不会错误 invalidate Tenant / Principal；真正 ancestor dependency 改变仍然会明确产生 definition drift。

### Operation 是 Non-reactive Semantic Work

Cordis `ctx.inject()` 继续是 reactive plugin lifecycle（`A4`）。Semantic Operation 使用普通 Principal-owned child Fiber，先 materialize Operation-local provider，再一次性解析 required typed capability 为 immutable snapshot，最后只调用一次 `execute()`。

Provider churn 可能让已捕获 provider 后续不可用，但不会 re-enter 或重复 semantic work。这就是已 proven 的 `A6`。

### DSH Boundary 保持 Native

真实 public DSH AgentRegistry 在 create / resume 时收到 Operation / Principal caller-bound `ownerCtx`。Operation 不复制 Cordis 私有 scope state 到 `Agent.ctx`，也不发明平行 Agent tenant registry。

Product Ingress 与 Agent Integration 是 Runtime Core 前后的独立 semantic plane，参见 [`saas-boundaries.zh-CN.md`](./saas-boundaries.zh-CN.md)。

## M3 / M3.5 后的 Package 规则

Core 与本次 hardening 仍然不创建 `dsh-saas`。Capability token、Composition、Runtime、Operation 当前仍是一套连贯 ownership / lifecycle contract，继续留在 `dsh-multi-tenant` 内最轻。

这不是永久承诺。只有后续 implementation 真正证明独立 consumer/replacement/lifecycle/release/distribution boundary，新 package 才出现。

## P0 Promotion Status

Hardening 后 P0 Core 满足：

- typed capability identity 与真实 scope authority；
- deterministic / fail-fast Composition；
- scope-local canonical identity，不再与无关 descendant 错误耦合；
- `A1`–`A6` 全部 proven；
- Tenant / Principal isolation 可执行证明；
- Operation cancellation / teardown 有覆盖；
- Principal -> Operation -> 真实 DSH create/resume/failure 在 Node 22.19 / Node 24 上可执行；
- packed external consumer 执行同一 typed/locality contract。

下一阶段应该建立在这些规律上，但整个项目仍保持 prerelease 自由：如果新的 evidence 证明存在更好的全局结构，当前 implementation 依然可以重构。
