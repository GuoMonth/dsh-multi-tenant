# v0.3 P0 底座

v0.3 要把项目从 Multi-Tenant Runtime 推进成可组合 SaaS Framework 的基础。本文件固定工程方法与 P0 边界；M1–M3 Core Vertical Slice 现在已经用真实 Runtime 与 pinned DSH Agent seam 证明这套方法成立。

## P0 目标

P0 只回答三个架构问题：

1. **Composition** —— SaaS capability 如何声明、校验并映射到真实 Runtime scope，同时不再造第二套 DI Container。
2. **Operation** —— 一个 authenticated Principal 如何拥有一次用户可见工作，并通过 one-shot lifecycle boundary 驱动 DSH create / resume。
3. **Fail-fast validation** —— 非法 capability graph 与 canonical definition drift 如何在用户流量进入前失败。

Distribution、Marketplace、安装 UI、vendor-specific Auth、具体 production MCP integration、billing、audit、usage 产品都不是 P0。

## 强制开发顺序

```text
Spec
  ↓
Assumption Ledger
  ↓
Executable external probe / contract test
  ↓
强类型 + 状态模型
  ↓
Failing behavior test
  ↓
最小实现
  ↓
Vertical-slice CI proof
```

只要 public API 依赖的 blocking external assumption 在 `v0.3-assumptions.json` 里仍然是 `open`，这个 API 就不能定型。

## Evidence 分类

- **External probe** —— 在精确支持 baseline 上证明 DSH / Cordis 拥有的行为；
- **Contract test** —— 独立于具体生产 provider，证明仓库拥有的 replaceable seam；
- **Conformance test** —— 证明 isolation / publication / teardown 等跨组件 invariant；
- **Vertical slice** —— 证明真实 Principal -> Operation -> DSH execution path；
- **Packed consumer smoke** —— 证明 npm tarball 暴露并执行与 workspace source 相同的 contract。

读 upstream source 适合发现 hypothesis，但不能代替 blocking assumption 的 executable proof。

## P0 架构边界

```text
SaaSDefinition
      ↓ compile
CompositionPlan       immutable、deterministic、带 fingerprint
      ↓ materialize
Tenant / Principal capability graph
      ↓
Principal-owned one-shot Operation
      ↓ capability snapshot
DSH ownerCtx / Agent setup-publication seam
```

Composition 层只负责 selection、scope placement、dependency validation、canonical composition identity 与 bootstrap ordering。Service resolution、Context isolation、Fiber lifetime、cleanup 继续属于 Cordis。

**禁止新增第二套 ServiceRegistry / ProviderContainer / generic DI resolver。** 如果设计开始复制 Cordis，说明抽象方向错了。

## 已经证明的 P0 决策

### Scope 必须是真实 Ownership

`deployment | tenant | principal | operation` 是真实 lifecycle / authority level。Ambient provider 只允许 deployment；非 deployment provider 必须真的在自己声明的 scope materialize。

### Canonical Composition Identity

Deterministic Plan fingerprint 会进入 canonical Tenant / Principal definition identity。Equivalent Plan 可以 join；structurally different Plan 会 fail，而不是悄悄共用 active node。

### Operation 是 Non-reactive Semantic Work

Cordis `ctx.inject()` 继续是 reactive plugin lifecycle（`A4`）。Semantic Operation 使用普通 Principal-owned child Fiber，先 materialize operation-local provider，再一次性解析 required capability 为 immutable snapshot，最后只调用一次 `execute()`。

Provider churn 可能让已经捕获的 provider 后续不可用，但不会 re-enter 或重复 semantic work。这就是 `A6`，现在已经 proven。

### DSH Boundary 保持 Native

真实 public DSH AgentRegistry 在 create / resume 时收到 Operation/Principal caller-bound `ownerCtx`。Operation 不复制 Cordis 私有 scope state 到 `Agent.ctx`，也不发明平行 Agent tenant registry。

## M3 后的 Package 规则

M3 以后仍然不创建 `dsh-saas` package。Composition 与 Operation 当前仍然扩展同一套 Runtime ownership contract，并作为 `dsh-multi-tenant` public subpath 存在。

这不是永久承诺。只有 M4/M5 的真实 capability contract 证明独立 consumer/replacement/lifecycle/release/distribution boundary 时，新 package 才出现。

## P0 Promotion Status

P0 Core 现在已经满足 promotion gate：

- ownership / state model 已有 Spec；
- `A1`–`A6` 全部 proven；
- 非法 composition 有 semantic fail-fast error；
- Tenant / Principal isolation 可执行证明；
- Operation cancellation / teardown 有覆盖；
- Principal -> Operation -> 真实 DSH create/resume/failure 在 Node 22.19 / Node 24 上可执行；
- packed external-consumer path 已覆盖。

项目现在可以进入 M4/M5 capability contract，不需要重新打开 Composition / Operation substrate，除非后续新证据证明当前模型错误。
