# v0.3 P0 Foundation

v0.3 changes the project from a Multi-Tenant Runtime into the foundation of a composable SaaS Framework. This document fixes the engineering method and the P0 boundary; the M1–M3 Core Vertical Slice now proves that method against the real Runtime and pinned DSH Agent surface.

## P0 objective

P0 asks exactly three architecture questions:

1. **Composition** — how SaaS capabilities are declared, validated and mapped onto real Runtime scopes without creating a second DI container.
2. **Operation** — how one authenticated Principal owns one user-visible unit of work and drives DSH create/resume through a one-shot lifecycle boundary.
3. **Fail-fast validation** — how invalid capability graphs and canonical definition drift fail before user traffic.

Distribution, Marketplace, installation UI, vendor-specific Auth, concrete production MCP integrations, billing, audit and usage products are not P0.

## Required development sequence

```text
Spec
  ↓
Assumption Ledger
  ↓
Executable external probe / contract test
  ↓
Strong types + state model
  ↓
Failing behavior test
  ↓
Smallest implementation
  ↓
Vertical-slice CI proof
```

A public API must not depend on a blocking external assumption while it remains `open` in `v0.3-assumptions.json`.

## Evidence classes

- **External probe** — behavior owned by DSH/Cordis on the exact supported baseline.
- **Contract test** — replaceable repository-owned seam independent of one production provider.
- **Conformance test** — cross-component invariants such as isolation/publication/teardown.
- **Vertical slice** — the real Principal -> Operation -> DSH execution path.
- **Packed consumer smoke** — the npm tarball exposes and executes the same contract as workspace source.

Reading upstream source is useful for discovering a hypothesis; it does not replace executable proof for a blocking assumption.

## P0 architecture boundary

```text
SaaSDefinition
      ↓ compile
CompositionPlan       immutable, deterministic, fingerprinted
      ↓ materialize
Tenant / Principal capability graph
      ↓
Principal-owned one-shot Operation
      ↓ capability snapshot
DSH ownerCtx / Agent setup-publication seam
```

The composition layer owns selection, scope placement, dependency validation, canonical composition identity and bootstrap ordering. Cordis continues to own service resolution, Context isolation, Fiber lifetime and cleanup.

**Do not add another ServiceRegistry / ProviderContainer / generic DI resolver.** If a design starts reproducing Cordis, the abstraction is wrong.

## P0 decisions now proven

### Scope means ownership

`deployment | tenant | principal | operation` are real lifecycle/authority levels. An ambient provider is deployment-only; non-deployment providers must actually materialize in their declared scope.

### Canonical composition identity

A deterministic Plan fingerprint participates in canonical Tenant/Principal definition identity. Equivalent Plans may join; structurally different Plans fail instead of silently sharing an active node.

### Operation is non-reactive semantic work

Cordis `ctx.inject()` remains reactive plugin lifecycle (`A4`). A semantic Operation uses a normal Principal-owned child Fiber, materializes operation-local providers, resolves required capabilities once into an immutable snapshot, and invokes `execute()` once.

Provider churn can make a captured provider unusable, but cannot re-enter or duplicate semantic work. This is `A6`, now proven.

### DSH boundary remains native

The real public DSH AgentRegistry receives the Operation/Principal caller-bound `ownerCtx` for create/resume. Operation does not copy Cordis private scope state into `Agent.ctx` and does not invent a parallel Agent tenant registry.

## Package rule after the M3 gate

No `dsh-saas` package is created after M3. Composition and Operation currently extend the same Runtime ownership contract and remain public subpaths of `dsh-multi-tenant`.

This is not a permanent promise. M4/M5 may justify a new package only if real capability contracts prove an independent consumer/replacement/lifecycle/release/distribution boundary.

## P0 promotion status

The P0 core now satisfies the promotion gates:

- state/ownership models are specified;
- assumptions `A1`–`A6` are proven;
- invalid composition has semantic fail-fast errors;
- Tenant/Principal isolation is executable;
- Operation cancellation/teardown is covered;
- Principal -> Operation -> real DSH create/resume/failure is executable on Node 22.19 and Node 24;
- the packed external-consumer path is exercised.

The project can now move to M4/M5 capability contracts without reopening the Composition/Operation substrate unless new evidence disproves it.
