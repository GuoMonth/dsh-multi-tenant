# v0.3 P0 Foundation

v0.3 changes the project from a Multi-Tenant Runtime into the foundation of a composable SaaS Framework. This document fixes the engineering method and the P0 boundary before implementation expands.

## P0 objective

P0 has exactly three architecture questions:

1. **Composition** — how SaaS capabilities are declared, validated and mapped onto Runtime scopes without creating a second DI container.
2. **Operation** — how an authenticated Principal starts one user-visible unit of work and drives DSH Agent create/resume through a Principal-derived lifecycle boundary.
3. **Fail-fast validation** — how invalid capability graphs fail before user traffic rather than during the first Agent call.

Distribution, Marketplace, installation UI, vendor-specific Auth, concrete MCP integrations, billing, audit and usage products are not P0.

## Required development sequence

Every P0 feature follows this order:

```text
Spec
  ↓
Assumption Ledger
  ↓
Executable external probe / contract test
  ↓
Strong types + state model
  ↓
Failing behavior test
  ↓
Smallest implementation
  ↓
Vertical-slice CI proof
```

A public API must not depend on a blocking external assumption while that assumption is `open` in `v0.3-assumptions.json`.

## Evidence classes

- **External probe** — proves behavior owned by DSH/Cordis using the exact supported baseline.
- **Contract test** — proves a replaceable repository-owned seam independently of a production implementation.
- **Conformance test** — proves cross-component invariants such as isolation, publication ordering and teardown.
- **Vertical slice** — proves the real path from Principal to Operation to DSH behavior.

Reading upstream source is useful for discovering a hypothesis; it does not replace an executable proof for a blocking assumption.

## P0 architecture boundary

```text
SaaSDefinition
      ↓ normalize
CompositionPlan       immutable, validated, no unresolved ambiguity
      ↓ bootstrap
Tenant / Principal capability graph
      ↓
Principal Operation
      ↓
DSH ownerCtx / Agent setup-publication seam
```

The composition layer owns selection, scope placement, dependency validation and bootstrap ordering. Cordis continues to own service resolution, injection, Fiber lifetime and cleanup.

**Do not add another ServiceRegistry / ProviderContainer / generic DI resolver.** If the design starts reproducing Cordis, the abstraction is wrong.

## Package rule

No v0.3 package is created by this foundation PR. A package may appear only after the implementation proves an independent consumer API, replacement boundary, lifecycle/composition boundary, version/release boundary, or Distribution boundary.

Capability names such as Auth, Credentials, MCP and Transport are not package names by default.

## P0 promotion gates

A P0 abstraction becomes public only when:

- its state/ownership model is specified;
- every blocking external assumption it depends on is `proven`;
- invalid configurations have semantic fail-fast errors;
- Tenant A/B and Principal sibling isolation are covered;
- teardown/cancellation behavior is covered;
- the Principal -> Operation -> DSH vertical slice is executable in CI.

## Current deliberate open gate

Cordis `ctx.inject()` is dependency-reactive. It may unload and re-run its callback when a required service disappears and later returns. That is desirable for long-lived plugins but dangerous if a callback is interpreted as exactly-once user work.

Therefore the final Operation API remains blocked until we prove a one-shot dependency-acquisition/lifecycle model that cannot duplicate externally visible work during provider churn. See assumption `A6` and [`operation-lifecycle.md`](./operation-lifecycle.md).
