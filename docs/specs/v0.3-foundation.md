# v0.3 P0 Foundation

v0.3 changes the project from a Multi-Tenant Runtime into the foundation of a composable SaaS Framework. This document fixes the engineering method and the durable P0 laws; implementation details remain revisable when vertical-slice evidence reveals a better structure.

## P0 objective

P0 asks three architecture questions:

1. **Composition** — how SaaS capabilities are declared, validated and mapped onto real Runtime scopes without creating a second DI container.
2. **Operation** — how one canonical Principal owns one user-visible unit of work and drives DSH create/resume through a one-shot lifecycle boundary.
3. **Fail-fast validation** — how invalid capability graphs and real canonical creation drift fail before user traffic.

Distribution, Marketplace, installation UI, vendor-specific Auth, production provider breadth, billing, audit and usage products are not P0.

## Required development sequence

```text
Spec
  ↓
Assumption Ledger
  ↓
Executable external probe / contract test
  ↓
Strong types + state model
  ↓
Failing behavior test
  ↓
Smallest implementation
  ↓
Vertical-slice CI proof
```

A public API must not depend on a blocking external assumption while it remains `open` in `v0.3-assumptions.json`.

The sequence is evidence-driven, not one-way. A later vertical slice may invalidate an earlier data model; when that happens, refactor the model and update the live Spec rather than preserving prerelease debt.

## Evidence classes

- **External probe** — behavior owned by DSH/Cordis on the exact supported baseline.
- **Contract test** — replaceable repository-owned seam independent of one production implementation.
- **Conformance test** — cross-component invariants such as isolation/publication/teardown/locality.
- **Vertical slice** — the real Principal -> Operation -> DSH execution path.
- **Packed consumer smoke** — the npm tarball exposes and executes the same contract as workspace source.

Reading upstream source is useful for discovering a hypothesis; it does not replace executable proof for a blocking assumption.

## P0 architecture boundary

```text
Typed CapabilityToken<T, Scope>
      ↓
SaaSDefinition
      ↓ compile
CompositionPlan
  ├─ whole-plan fingerprint
  └─ scope-local dependency-closure fingerprints
      ↓ materialize
Tenant / Principal capability graph
      ↓
Principal-owned one-shot Operation
      ↓ typed immutable capability snapshot
DSH ownerCtx / Agent setup-publication seam
```

Composition owns semantic capability identity, provider selection, scope placement, dependency validation, local canonical creation identity and bootstrap ordering. Cordis continues to own service resolution, Context isolation, Fiber lifetime and cleanup.

**Do not add another ServiceRegistry / ProviderContainer / generic DI resolver.** If a design starts reproducing Cordis, the abstraction is wrong.

## Durable P0 decisions

### Capability identity is semantic and typed

A capability binds stable Cordis service key, TypeScript value type and lifecycle/authority scope in one `CapabilityToken<T, Scope>`.

This removes caller-side type assertions such as `require<MyType>('credentials')` and prevents key/scope metadata from drifting independently.

Typed helpers remain thin Cordis facades; they do not own resolution.

### Scope means ownership

`deployment | tenant | principal | operation` are real lifecycle/authority levels. Ambient external capabilities are deployment-only; non-deployment providers must actually materialize in their declared scope.

### Canonical composition identity is local

A whole Plan fingerprint is useful for exact comparison and diagnostics, but it is too coarse for canonical parent identity.

Canonical Tenant/Principal creation uses a **scope-local provider dependency closure**:

```text
scope-owned providers
+ selected ancestor providers they actually depend on
```

Therefore unrelated Operation evolution does not falsely invalidate a Tenant/Principal, while a real ancestor dependency change still creates explicit definition drift.

### Operation is non-reactive semantic work

Cordis `ctx.inject()` remains reactive plugin lifecycle (`A4`). A semantic Operation uses a normal Principal-owned child Fiber, materializes Operation-local providers, resolves required typed capabilities once into an immutable snapshot and invokes `execute()` once.

Provider churn can make a captured provider unusable, but cannot re-enter or duplicate semantic work. This is `A6`, proven.

### DSH boundary remains native

The real public DSH AgentRegistry receives the Operation/Principal caller-bound `ownerCtx` for create/resume. Operation does not copy Cordis private scope state into `Agent.ctx` and does not invent a parallel Agent tenant registry.

Product Ingress and Agent Integration are separate semantic planes around the Runtime Core; see [`saas-boundaries.md`](./saas-boundaries.md).

## Package rule after M3/M3.5

No `dsh-saas` package is created by the Core or this hardening pass. Capability tokens, Composition, Runtime and Operation still form one coherent ownership/lifecycle contract inside `dsh-multi-tenant`.

This is not a permanent promise. A new package appears only when later implementation proves an independent consumer/replacement/lifecycle/release/distribution boundary.

## P0 promotion status

The hardened P0 core satisfies:

- typed capability identity and real scope authority;
- deterministic/fail-fast Composition;
- scope-local canonical identity rather than false descendant coupling;
- assumptions `A1`–`A6` proven;
- Tenant/Principal isolation executable;
- Operation cancellation/teardown covered;
- Principal -> Operation -> real DSH create/resume/failure executable on Node 22.19 and Node 24;
- packed external-consumer execution of the same typed/locality contract.

The next product-facing stage should build on these laws, but the project remains free to refactor any prerelease implementation if new evidence shows a better global structure.
