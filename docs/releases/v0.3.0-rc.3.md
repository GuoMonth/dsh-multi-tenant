# dsh-multi-tenant 0.3.0-rc.3 — Durable Local Experience

`0.3.0-rc.3` removes the next barrier after the First Product Experience: an individual developer can now prove durable multi-tenant Session ownership across restart without provisioning PostgreSQL, Docker or a native SQLite addon.

## Product path

The supported first-use path is now:

```text
existing JWT / Cookie / req.user
  -> product-owned authentication
  -> TrustedSubject
  -> canonical Tenant / Principal
  -> Tenant MCP config + Principal credentials
  -> Principal-aware Agent create/resume
  -> immutable SQLite Session ownership
  -> restart-safe local development
  -> official @deepseek-ai/dsh-mcp-client
  -> real MCP Tool
```

## Zero-external-service durable local store

The shipped DSH bundle now selects `dsh-multi-tenant/sqlite-store` instead of the in-memory reference provider.

`SQLiteTenantSessionStore`:

- uses Node's built-in `node:sqlite` only;
- adds no npm database dependency or native addon;
- defaults to `<cwd>/.dsh-multi-tenant/session-ownership.sqlite`;
- supports `DSH_MULTI_TENANT_SQLITE_PATH` and direct `{ path }` configuration;
- creates its parent directory automatically;
- uses WAL, `synchronous=NORMAL` and a bounded busy timeout;
- implements claim-once ownership with one atomic `INSERT ... ON CONFLICT DO NOTHING`;
- preserves same-owner idempotency and cross-Principal/cross-Tenant conflict semantics;
- closes its database with the owning Cordis lifetime.

The database stores only opaque Session ownership (`session_id`, `tenant_id`, `user_id`). It does not become a user database, credential vault, Agent persistence store or audit database.

`InMemoryTenantSessionStore` remains available for hermetic tests and custom compositions.

## Permanent restart and competition evidence

The new permanent command:

```sh
pnpm probe:sqlite
```

uses the built package and launches independent Node processes against one SQLite file. It proves:

- first owner claim succeeds;
- a fresh process sees the persisted owner;
- same owner re-claim is idempotent;
- Acme/Bob cannot take Acme/Alice's Session;
- Globex/Alice cannot take an Acme Session;
- two independent processes racing for a fresh Session produce exactly one `created` and one `conflict` result;
- both processes observe the same immutable winner.

The package test suite also runs the reusable `TenantSessionStore` contract against SQLite and covers restart plus competing connections.

`pnpm release:check` now includes `probe:sqlite`, and the Node 22.19 / Node 24 package-contract CI lanes run the same proof after build.

## Public surface

A new public subpath is shipped:

```text
dsh-multi-tenant/sqlite-store
```

It exports `SQLiteTenantSessionStore`, `SQLiteTenantSessionStoreConfig` and `defaultSQLiteTenantSessionStorePath()`.

The release preflight requires the subpath and permanent proof to remain present.

## Acknowledged DSH Web boundary — #41

This release explicitly accepts the current pinned-DSH limitation: product Principal authority is not materialized automatically for every stock DSH Web RPC business method.

That boundary is not hidden behind the starter and is not solved by SQLite. The recommended production deployment until DSH exposes a request-scoped authority seam is:

```text
Browser / external client
        ↓
Product Gateway / BFF
  - authenticate
  - resolve canonical Tenant / Principal
  - authorize protected Session / Agent resources
        ↓ private network / loopback
DSH Web + dsh-multi-tenant
```

Public clients must not be able to bypass the Product Gateway and reach stock DSH `/api` directly. `dsh-multi-tenant` continues to enforce its own fail-closed Session ownership and Principal-bound Agent admission as defense in depth.

Issue #41 remains open as a future DSH-native integration improvement, not a blocker for this production deployment contract.

## Scope boundary

SQLite is intentionally the **local durable / single-node adoption provider**. `0.3.0-rc.3` does not claim:

- horizontally scaled multi-replica Session ownership persistence;
- PostgreSQL/Redis/MySQL production backends;
- universal OAuth/OIDC/token-refresh or Credential Broker behavior;
- Permission/Policy or full Audit/OTel product features;
- hostile-code process/filesystem/network isolation;
- automatic tenant authorization for every stock DSH Web RPC.

A future PostgreSQL or other multi-instance provider should satisfy the existing `TenantSessionStore` contract when real deployments require it.

## Compatibility

- Node: `^22.19.0 || >=24.0.0`
- Cordis: `>=4.0.1 <5`
- pinned DSH baseline: `0.1.1-rc.2` @ `b150a551b8d465e31e418e1b2eaf5e79bbb7d28e`
