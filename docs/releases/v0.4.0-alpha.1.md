# dsh-multi-tenant 0.4.0-alpha.1

Status: **release-ready source, intentionally unpublished**. The correction wave and second adversarial closure review completed on 2026-09-03. Publication, a Git tag, and a GitHub Release remain separate explicit actions and were not performed.

## Stable direction

The project has one job: provide Principal-scoped DSH Agent resources for multi-tenant hosts. The small authority kernel remains:

```text
trusted PrincipalContext
  -> plugin-minted AgentId
  -> Principal-scoped SQLite lookup
  -> host capability/isolation protocols
  -> native DSH Agent / Session / MCP lifecycle
```

The removal of the `0.3` Session-claim, APIProxy, global MCP-name hashing, generic composition/capability/operation framework, and compatibility layer remains correct. Sunk cost does not change that decision.

## Retrospective findings

The first retrospective overstated four properties:

1. The projected `withAgent()` runtime had the right shape but could be retained after its callback, escaping the intended authority/lifecycle scope.
2. Web Agent creation shallow-validated nested DSH options and then forwarded caller-controlled fields.
3. The DSH/MCP integration used the official MCP client and AgentRegistry seam but replaced the Agent factory/session; it was not a complete native DSH lifecycle proof.
4. Default SQLite permissions, single-process wording, and mutable GitHub Action inputs did not yet match the claimed trust boundary. The review also incorrectly called pnpm 11's `minimumReleaseAgeExclude` inactive: pnpm already defaults the age gate to 1,440 minutes, so the real problems were relying on an implicit default and retaining stale alpha.4 exceptions.

All four findings were corrected without adding a general policy framework:

- `withAgent()` now creates a fresh callback capability and invalidates all six operations on settlement or lifecycle revocation; the decorative `policyRevision` was deleted.
- Web creation accepts only `{}` or a named profile resolved by trusted host code; both wire and service options are rebuilt from closed allowlists.
- DSH is pinned to the current `0.1.2-alpha.5` source. A deterministic integration uses stock AgentLoop, SessionStore/projections, JSONL persistence, ToolRuntime, and the official MCP client across create, restart, same-session resume, and delete.
- The default Unix SQLite path enforces directory `0700` and database `0600`; explicit paths stay host-owned. Workflows use full reviewed SHAs, repository SHA enforcement is enabled, and pnpm's 1,440-minute age policy plus exact alpha.5 exceptions are explicit.

A second adversarial review found that `delete()` awaited authorization before reserving its serialized position. A later `withAgent()` could overtake deletion, resume a cancelled Agent, and enter its callback before tombstoning. Deletion now starts scoped authorization and synchronously reserves an admission barrier; authorization revokes active views immediately, while every later open remains behind the durable tombstone. Unauthorized deletion never touches the live Agent.

- [#52](https://github.com/GuoMonth/dsh-multi-tenant/issues/52): adversarial Web fields and malformed resolver output are denied before service/DSH work; bilingual examples expose only the product-level profile.
- [#45](https://github.com/GuoMonth/dsh-multi-tenant/issues/45): the real DSH lifecycle uses no replacement factory or fake Session, proves two Agents with one raw MCP server name, persists injected events, rejects foreign owners before resume, and leaves log deletion to DSH.
- [#53](https://github.com/GuoMonth/dsh-multi-tenant/issues/53): Unix mode checks, explicit-path non-interference, immutable workflow scanning, frozen install, source identity, Node 22.19/24, and packed-consumer checks all run through `pnpm release:check`/CI.
- The latest upstream release was re-queried at review time; it remains DSH `0.1.2-alpha.5` at `db6bdc3576c2d4e7c965e8e3ed0c2a731eed87f5`.

`0.4.0-alpha.2` remains limited to [#49](https://github.com/GuoMonth/dsh-multi-tenant/issues/49), which deterministically reconciles abandoned provisioning under the declared single-active-process host invariant without locks or fencing, and [#50](https://github.com/GuoMonth/dsh-multi-tenant/issues/50), which propagates cooperative lifecycle abort and validates provider contracts without forcing arbitrary code or certifying host isolation.

## Explicit limits

- The default shared provider is logical same-process isolation, not a hostile-code boundary.
- The built-in SQLite topology is currently local, single-node, and single-process; it is not a distributed ownership service.
- Typert public ingress is absent because stock DSH has no trustworthy product-Principal binding. Stock DSH `/api` remains private/administrative.
- Agent deletion revokes plugin access and scrubs its directory record; it does not claim physical erasure of DSH logs.
- Host authentication, secret storage, public network exposure, and real process/container isolation remain host responsibilities expressed through narrow protocols.
- Delete/shutdown drain is cooperative; a callback or host provider acquisition that ignores abort or never settles can delay completion. #50 improves signal propagation and contract validation but deliberately adds no forced interruption or arbitrary default timeout.
- No `0.3` API or data migration is provided.

最终证据覆盖 callback resolve/reject 与 delete/revoke/refresh/shutdown、Web profile/恶意字段、默认 Unix `0700/0600` 与显式路径不干预、原生 DSH alpha.5 AgentLoop + JSONL + MCP 的 create/restart/resume/delete、精确 source identity、Node 22.19/24、frozen install 和 packed consumer。复盘时重新查询的最新 DSH 仍是 `0.1.2-alpha.5` / `db6bdc3576c2d4e7c965e8e3ed0c2a731eed87f5`。
