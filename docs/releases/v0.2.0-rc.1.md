# dsh-multi-tenant v0.2.0-rc.1

`0.2.0-rc.1` opens the v0.2 line with a new project goal: **make DeepSeek Harness a real Multi-Tenant Runtime**.

## Version-line decision

The published v0.1 tags are frozen historical contracts. No new feature work is planned on the v0.1 line.

v0.1 remains the authorization kernel:

- minimal authenticated `TenantPrincipal`;
- immutable session ownership;
- fail-closed access decisions;
- replaceable ownership-store contract.

v0.2 keeps those guarantees and adds runtime capability isolation above them.

## What changed

### Context-native Tenant Runtime

A new `ctx.tenantRuntime` service can create canonical live tenant contexts and authenticated principal contexts.

Selected Cordis service names receive independent isolation labels per tenant or principal. Providers are mounted below the returned context and resolved by Cordis itself; the runtime does not introduce a parallel `tenantId -> service instance` dependency container.

### Defense in depth

The v0.1 ownership kernel deliberately stays deployment-global. Tenant contexts cannot isolate away `multiTenant`, `tenantSessionStore`, `tenantRuntime`, or Cordis core services.

The resulting model is:

1. Context-native capability isolation by construction.
2. Persistent session ownership authorization by invariant.
3. Strong process/filesystem/network isolation remains a deployment concern.

### Scope-plane separation

DSH already uses `@deepseek-ai/dsh-scope` for Agent/Preset registration visibility. Agent Presets use the Agent scope parent relation, so v0.2 does not overload that same parent chain with tenancy.

Cordis service isolation owns tenant/principal capability providers; DSH scope routing continues to own Agent/Preset tools, prompts and listeners.

### Compatibility baseline

This PR intentionally keeps the repository's already-proven executable DSH dependency closure at `0.1.0-rc.7`. The current upstream `0.1.1-rc.2` scope/preset implementation was reviewed while designing v0.2, but upgrading the complete DSH package graph and lockfile is a separate follow-up rather than being mixed into this architecture change.

## Known ecosystem gaps

Context isolation cannot make an upstream plugin tenant-aware when the plugin itself uses deployment-global state outside Cordis service resolution.

One known example in the reviewed current upstream is the DSH MCP client: live `serverName` reservations are keyed by `ctx.root`. Two tenant-local MCP instances therefore cannot automatically reuse the same `serverName` without a provider/upstream change or unique names.

This release records such surfaces as compatibility work instead of hiding them behind another registry.

## Verification added

- two-tenant same-service isolation tests;
- principal-local credential isolation tests;
- duplicate tenant graph rejection;
- cross-tenant principal binding rejection;
- explicit proof that the v0.1 ownership kernel stays shared;
- packed external-consumer smoke for the `dsh-multi-tenant/runtime` entry point;
- bundle manifest checks for the new `tenant-runtime` row.

## Not included

`0.2.0-rc.1` is not a complete Web/Auth/MCP product integration and is not a process sandbox. HTTP/WebSocket authentication must still bind an authenticated principal to the correct runtime context before work is driven. Strong isolation remains a container/Pod boundary.
